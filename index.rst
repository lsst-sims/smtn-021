###################################################################
Feature Based Scheduler Configuration for the Start of Rubin's LSST
###################################################################

.. abstract::

   This note describes the configuration of the Feature Based Scheduler (FBS)
   used to run the Legacy Survey of Space and Time (LSST) with the Simonyi
   Survey Telescope and LSSTCam. The configuration is assembled in
   ``ts_config_scheduler`` from survey-building functions in ``ts_fbs_utils``,
   which in turn use the scheduling framework provided by ``rubin_scheduler``.
   We describe the survey footprint, the masks and cloud-avoidance limits
   applied to all surveys, and each tier of surveys in the scheduler, in
   priority order.

.. _sec-introduction:

Introduction
============

The Feature Based Scheduler :cite:`Naghib2019` selects each visit by
evaluating a set of *surveys* against the current conditions (time, sky
brightness, seeing, clouds, telescope state and the history of previous
visits). Each survey combines a list of *basis functions* — usually HEALpix
maps over the sky — with a set of weights to produce a reward. Some basis
functions act purely as masks: they carry a weight of zero, but any pixel they
set to ``NaN`` is unavailable to that survey. The survey with the highest
reward generates one or more observations, which are then adjusted by the
survey's *detailers* (for example to set the camera rotation angle, apply
dithers, or order visits by band) before being placed in the observing queue.

Surveys are grouped into *tiers*. At each decision point the
``CoreScheduler`` evaluates the tiers in order: if any survey in the first
tier has a finite reward, the highest-reward survey in that tier is chosen and
lower tiers are not considered. Only if no survey in a tier is feasible does
the scheduler move on to the next tier. The order of the tiers therefore sets
the priority of the different survey components, while the basis function
weights decide between surveys within a tier.

The LSST configuration is spread across three packages:

``rubin_scheduler``
   The scheduling framework: the ``CoreScheduler``, the survey classes, basis
   functions, detailers and footprint utilities. See the
   `rubin_scheduler documentation <https://rubin-scheduler.lsst.io>`_.

``ts_fbs_utils``
   Functions which build the individual surveys and footprints used at the
   observatory, with the observatory's default parameters
   (``lsst.ts.fbs.utils.maintel``). Most of the survey design lives here.

``ts_config_scheduler``
   The deployed configuration. The LSST scheduler is built by
   ``Scheduler/feature_scheduler/maintel/fbs_config_lsst_survey.py``, which
   sets the survey-level parameters and calls the ``ts_fbs_utils`` functions.
   The Scheduler CSC configuration (yaml) files that point to this
   configuration are in ``Scheduler/v10``.

This note describes the configuration at the versions listed in
:numref:`tab-versions`. Where a value is set in the configuration file, that
value is quoted; otherwise the default in ``ts_fbs_utils`` or
``rubin_scheduler`` applies.

.. _sec-footprint:

Survey footprint
================

The footprint is generated by
``lsst.ts.fbs.utils.maintel.lsst_footprints.get_footprints``, called from the
configuration as::

   footprints, template_fp, footprint_mask = lsst_footprints.get_footprints(
       nside=nside,
       bandpasses=("u", "g", "r", "i", "z", "y"),
   )

It returns three objects:

``footprints``
   The time-dependent survey footprint (a ``Footprints`` object), including
   the rolling cadence. This is used by the pairs, long-gaps and greedy
   surveys to decide where visits are needed.

``template_fp``
   A flat footprint used by the template surveys, from which areas that
   already have templates have been removed.

``footprint_mask``
   A HEALpix mask of the full LSST footprint, used to restrict the ToO and
   near-sun twilight surveys.

Survey start
------------

The footprint evolves with time from a fixed survey start,
``SURVEY_START_MJD``, defined in ``lsst_footprints`` as 2026-06-29T12:00:00
(MJD 61220.5). This value is imported by the configuration, ``lsst_surveys``
and the DDF pre-scheduling scripts so that all parts of the survey use the
same start date. It sets the phase of the rolling cadence (through the RA of
the Sun at the start of the survey) and the start of the template seasons.

--------------

(currently the ``Phase3AreaMap``). This divides the sky into labelled
regions, each with a relative weight per band. The weights set the desired
ratio of visits between regions and bands, normalized so that the low-dust
WFD region in *r* has a value of 1. Regions are assigned in the order listed in
:numref:`tab-regions`; once a pixel is labelled, later regions do not
overwrite it.

The ``bandpasses`` argument to ``get_footprints`` restricts the footprint to
a subset of bands: the footprint in any band not listed is set to zero, in
both the survey and template footprints. This is the place to remove a band
from the survey. The region labels are computed before this restriction, so
the rolling area does not change when bands are removed.

Rolling cadence
---------------

The pixels labelled ``lowdust`` or ``virgo`` form the rolling area. Outside
this area, the footprint accumulates visits at a constant rate. Within it,
``make_rolling_footprints`` divides the rolling area, separately north and
south of the Galactic plane, into four declination bands of equal area.
Alternate bands are assigned to each of two slices, and the slices take turns
receiving more visits in each observing season. The parameters used are
listed in :numref:`tab-rolling`.

.. _tab-rolling:

.. list-table:: Rolling cadence parameters.
   :header-rows: 1

   * - Parameter
     - Value
     - Meaning
   * - ``roll_n_slice``
     - 2
     - Number of slices (each made of two alternating declination bands).
   * - ``roll_scale``
     - 0.9
     - Strength of rolling (1 is full rolling, 0 is none).
   * - ``roll_uniform``
     - True
     - Use "uniform" rolling, with a uniform season between rolling cycles.
   * - ``u5``
     - True
     - Use the hard-coded season sequence below.
   * - ``roll_n_cycles``
     - 3
     - Not used when ``u5`` is set.

With ``nslice = 2`` and ``scale = 0.9``, a slice in its low ("D") season
receives :math:`1 - 0.9 = 0.1` of its uniform rate and a slice in its high
("U") season receives :math:`2 - 0.1 = 1.9` of its uniform rate. A uniform
season ("1") receives its uniform rate. Because ``uniform`` is set, each slice
is further split by RA relative to the Sun at the survey start, so that the
part of each slice which is first observable later in the year starts its
sequence one season later. With ``u5`` the season sequence for each slice is
fixed:

* two uniform seasons;
* one rolling cycle (one low and one high season);
* a uniform season (the fifth season);
* two further rolling cycles;
* uniform seasons for the remainder of the survey.

The two slices are always out of phase, so that the total WFD rate remains
roughly constant.

Template footprint
------------------

Difference imaging needs template images in each band over the whole
footprint, and templates must be built quickly in the early part of the
survey. The template footprint is a separate ``Footprint`` that does not roll.
It is set to 1 everywhere the survey footprint is non-zero in a band. Pixels
which already have templates are then removed, using the coverage maps read
by ``rubin_scheduler``'s ``get_template_coverage`` (from the
``scheduler/template_maps`` files in ``rubin_sim_data``). The template
surveys (:ref:`sec-tier-templates`) use this footprint, together with seeing
limits, to target the areas still missing templates.

Footprint mask
--------------

``footprint_mask`` is 1 wherever the survey footprint in *r* is non-zero and
0 elsewhere. It restricts the ToO follow-up (:ref:`sec-tier-too`) and the
near-sun twilight microsurvey (:ref:`sec-tier-twilight`) to the LSST
footprint.

.. _sec-masks:

Standard masks and cloud avoidance
==================================

Every survey includes a common set of mask basis functions, generated by
``lsst_surveys.standard_masks``. These keep the telescope within its
operating limits and away from bright objects. They do not avoid clouds;
cloud avoidance is set separately for each tier (:ref:`sec-clouds`).

Standard masks
--------------

``standard_masks`` returns the mask basis functions listed in
:numref:`tab-masks`, all with weight zero.

.. _tab-masks:

.. list-table:: Mask basis functions returned by ``standard_masks``.
   :header-rows: 1

   * - Basis function
     - Purpose
   * - ``MoonAvoidanceBasisFunction``
     - Avoid pointings within ``moon_distance`` (30°) of the Moon, which can
       trip the camera electronics.
   * - ``PlanetMaskBasisFunction``
     - Avoid bright planets.
   * - ``MaskDirectWindBasisFunction``
     - Avoid pointing into the wind when the wind speed exceeds
       ``wind_speed_maximum``.
   * - ``AltAzShadowMaskBasisFunction``
     - Keep pointings within the altitude and azimuth limits, including any
       part of the sky which will move outside these limits within
       ``shadow_minutes``.
   * - ``AltAzShadowTimeLimitedBasisFunction``
     - Optional (``apply_time_limited_shadow``): during the last
       ``time_to_sunrise`` hours of the night, restrict the azimuth to
       ``min_az_sunrise`` to ``max_az_sunrise``, pointing away from sunrise.
   * - ``SunAltLimitBasisFunction``
     - Optional (``sun_alt_limit``): only observe while the Sun is below a
       given altitude.

Survey-specific mask settings
-----------------------------

Two settings are changed by individual tiers.

The maximum altitude is lowered from 86.5° to ``blob_max_alt = 76°`` for the
template, long-gaps, pairs and greedy surveys. These surveys move across the sky, and
pointings near zenith lead to long slews when they cross the meridian.

The ``shadow_minutes`` value is raised by each survey generator to the time
that survey needs to complete its sequence of visits, so that a field does not
move outside the altitude or azimuth limits before it is finished.
:numref:`tab-tier-masks` summarizes the resulting values.

.. _sec-clouds:

Cloud avoidance
---------------

Clouds are handled in several ways, using the cloud extinction maps provided
to the scheduler in the Conditions:

* A ``MaskCloudMapBasisFunction`` in a survey masks pixels where the cloud
  extinction is above that survey's ``extinction_limit`` (in magnitudes), so
  the survey will not choose those pointings.
* An ``ExtinctionLimitDetailer`` writes the survey's ``extinction_limit``
  into each observation it generates. When the queue manager checks the queue
  (``check_clouds=True``), it masks pointings using the smallest
  ``extinction_limit`` among the observations in the queue. This drops visits
  that have become clouded since the queue was filled.
* The queue manager also includes its own ``MaskCloudMapBasisFunction``, with
  an extinction limit of 3.0 magnitudes (:ref:`sec-assembly`). This applies
  to every queued observation and acts as an overall ceiling; it is set to the
  largest per-survey limit so that it does not override the tighter limits
  applied through ``check_clouds``.
* The ``M5DiffBasisFunction`` used by the pairs, long-gaps and greedy
  surveys includes cloud extinction in its estimate of the 5σ depth
  (``apply_clouds_m5``), so these surveys prefer clearer parts of the sky.
* The template surveys include a ``CloudedOutMapBasisFunction``, which makes
  the survey infeasible when the median extinction above the horizon is
  greater than ``median_cloud_limit`` (2.0 magnitudes).

.. _sec-tiers:

Survey tiers
============

The surveys are arranged in eight tiers (:numref:`tab-tiers`). The first
three tiers contain scripted surveys, which hold lists of specific visits
with time windows; when any of these visits can be observed, the survey
returns a very large reward and takes priority over everything below it. The
remaining tiers contain the "Markov" surveys, which build reward maps across
the sky from their basis functions and choose fields to observe in response
to the current conditions.

.. _tab-tiers:

.. list-table:: Survey tiers, in priority order.
   :header-rows: 1

   * - Tier
     - Surveys
     - Purpose
   * - 1
     - ToO (:ref:`sec-tier-too`)
     - Follow-up of gravitational wave, neutrino, Solar System and other
       Target of Opportunity alerts.
   * - 2
     - Roman Galactic Bulge (:ref:`sec-tier-roman`)
     - Regular visits to the Roman Galactic Bulge Time Domain Survey field.
   * - 3
     - Deep Drilling Fields (:ref:`sec-tier-ddf`)
     - Pre-scheduled sequences of visits to the five DDFs.
   * - 4
     - Templates (:ref:`sec-tier-templates`)
     - Acquire good-seeing template images across the footprint early in the
       survey.
   * - 5
     - Long gaps (:ref:`sec-tier-longgaps`)
     - Pairs of visits followed by a third visit several hours later.
   * - 6
     - Pairs (:ref:`sec-tier-blobs`)
     - The main wide-area survey: pairs of visits in contiguous "blobs".
   * - 7
     - Near-sun twilight (:ref:`sec-tier-twilight`)
     - Twilight observations at low solar elongation for near-Earth and
       interior Solar System objects.
   * - 8
     - Greedy (:ref:`sec-tier-greedy`)
     - Single visits to fill any remaining time.

Each scripted survey has an ``ignore_obs`` list. Observations whose
``scheduler_note`` contains any of these strings are ignored by the survey
when it updates its internal state, so that, for example, a pairs visit
which happens to land on a DDF does not count as one of the scheduled DDF
visits.

.. _sec-tier-too:

Tier 1: Targets of Opportunity
------------------------------

The ToO surveys are generated by ``too_surveys.gen_too_surveys``. Each is a
``ToOScriptedSurvey`` which watches the Targets of Opportunity in the
Conditions (supplied to the Scheduler CSC by the SCiMMA alert stream; see
:ref:`sec-running`). When a new alert of a type the survey follows arrives,
the survey generates a script of follow-up visits:

* The alert's sky map is multiplied by the footprint mask
  (:ref:`sec-footprint`), so only the part of the alert region which lies
  inside the LSST footprint is followed up. If no HEALpix in the sky map
  falls within the footprint, the alert center is used if it is within the
  footprint; otherwise the alert is ignored.
* The region is tiled with LSSTCam pointings. When a region needs more than
  one pointing, the tiling is rotated randomly for each visit, so that
  repeated visits are dithered across chip and raft gaps.
* For each time in the survey's sequence, visits are scheduled in each of the
  listed bands, with the given number of visits per band and exposure time.
  Each visit can be observed from one hour before its scheduled time until
  the flush time after it.

When a scheduled visit is available, it must also be at altitude 25°–85°,
within ±5 hours of the meridian, and pass the masks. A ToO survey with
available visits has a reward of :math:`10^6`, so ToO follow-up takes
precedence over all other surveys. The ToO surveys respond to the alert types
in :numref:`tab-too`.

Some ToO surveys adjust the bands used:

* For binary black hole mergers (``ToO, BBH``), the default bands are rzi.
  In dark time (Moon illumination below 50%), z is replaced by g, and if the
  alert's posterior distance is less than 2200 Mpc, r is also replaced by u,
  giving gri for distant events and ugi for nearby events. These changes are
  only made if the new band is mounted.
* For surveys which use z band (``ToO, BBH`` and ``ToO, neutrino``), a
  ``BandSubstituteDetailer`` replaces z with y if z is not mounted. For
  ``ToO, SSO_twi``, z is replaced with i.
* ``ToO, GW_large`` returns at most 100 visits at a time, rather than the
  default 500.
* For ``ToO, SSO_night``, the sequence times are counted from the current
  time rather than the alert time when running in simulation
  (``for_simulation=True``).

Matching of alert types uses substrings: a survey follows an alert if any of
its alert type strings appears within the alert's type.

All ToO surveys use the same masks and detailers, which are set up in the
configuration:

* The standard masks (:ref:`sec-masks`), plus a cloud mask at 3.0 magnitudes
  of extinction. ToOs use the full 86.5° maximum altitude and the minimum
  ``shadow_minutes`` of 2 minutes.
* A ``CameraRotDetailer``, which sets a random camera rotation within the
  ±80° rotator limits.
* A ``BandSortDetailer``, to order visits by band and reduce filter changes.
* ``LabelRegionsAndDDFs``, which adds the survey region and any DDF name to
  the target name.
* An ``ExtinctionLimitDetailer`` with a 3.0 magnitude limit for the queue
  manager.

All ToO visits are single exposures, including the 120 s exposures for
``GW_case_A``.

Visits in each sequence are dithered by up to 0.2° in RA/Dec for each visit,
and the camera rotation is offset by 3° per visit within ±55° (with a random

band currently in use. The Roman surveys use the standard masks with the full
86.5° maximum altitude, plus a cloud mask and ``ExtinctionLimitDetailer`` at
the limits in :numref:`tab-roman`. They ignore observations from all other
surveys, including the DDFs, when tracking their own visits.

.. _sec-tier-ddf:

Tier 3: Deep Drilling Fields
----------------------------

The Deep Drilling Fields (DDFs) are observed by a single ``ScriptedSurvey``,
``deep drilling``, whose script is a pre-computed array of DDF visits for the
whole ten-year survey. Pre-computing the schedule lets each sequence be placed
at the best time in the night, and on nights spread evenly through each
field's observing season, which a reactive survey cannot easily do.

Fields
^^^^^^

The five DDFs are ELAIS-S1, XMM-LSS, ECDFS, COSMOS and the Euclid Deep Field
South (EDFS). EDFS is covered by two pointings, ``EDFS_a`` and ``EDFS_b``; the
visits of each EDFS sequence are split evenly between them.

Sequences
^^^^^^^^^

The DDF schedule is defined in ``define_ddf_seq`` in
``ts_config_scheduler/Scheduler/ddf_gen/gen_ddf_presched_observations.py``.
Each field-season is assigned a tier of depth, and each depth tier has a set
of sequence types (:numref:`tab-ddf-seq`). A sequence is a set of visits
taken together in one night; each sequence type is scheduled separately, on
at most one night per sequence type.

Scheduling the sequences
^^^^^^^^^^^^^^^^^^^^^^^^

``lsst_ddf_presched.generate_ddf_scheduled_obs`` turns these definitions into
scheduled visits, using a pre-computed grid of the airmass, sky brightness and
g-band 5σ depth at each DDF through the survey
(``scheduler/ddf_grid_fine.npz`` in ``rubin_sim_data``). For each sequence
type in each field-season:

#. The season is centered on the time the field is opposite the Sun, with
   the given season length; outside this the field is not scheduled.
#. Times are masked when the Sun is above −18°, the airmass is above 2.5, or
   the g-band 5σ depth (for a nominal 0.7" zenith seeing) is shallower than
   the minimum g depth. The mask is extended so the whole sequence fits
   before a masked time.
#. Sequences restricted by the Moon are only scheduled when the Moon
   illumination is below 40% (u-only sequences) or above 40% (y-only
   sequences). The g+i and r+z sequences are restricted to alternate nights,
   so these interleave.
#. The desired number of sequences is spread evenly through the season, and
   nights are chosen to match this cumulative distribution as closely as
   possible, with at most one sequence of each type per night. If there are
   too few usable nights, the number of sequences is reduced.
#. Within each chosen night, the sequence is scheduled at the time with the
   deepest g-band 5σ depth.

The scheduled visits have a time tolerance of 15 minutes and a position
tolerance of 3°. When they are executed they must be at altitude 25°–85°
with the Sun below −18°; the 30° Moon avoidance in the standard masks also
applies. Each visit remains in the script until its flush time
(:numref:`tab-ddf-seq`) after the scheduled time. Exposure times are 30 s,
or 38 s in u, with one exposure per visit.

   HA_min=21, HA_max=3 (intended as +/-3 h). ScriptedSurvey accepts visits
   with HA > HA_max or HA < HA_min, so these values exclude no hour angles.
   Update this paragraph once resolved.

The pre-computed array is stored in ``rubin_sim_data`` as
``scheduler/ts_ddf_array_<hash>.npz``, and the configuration loads it with
``read_ddf_obs_array``, checking that the hash in the file matches the
expected hash (``110273b``). This is generated with the start date
``SURVEY_START_MJD`` and the science program ``BLOCK-430`` by
``lsst_ddf_gen_block_430.py``. The hash and regeneration procedure are
described in :ref:`sec-maintaining`.

Survey masks and detailers
^^^^^^^^^^^^^^^^^^^^^^^^^^

When the scheduled visits are available, the ``deep drilling`` survey checks
them against the standard masks, with the full 86.5° maximum altitude and
``shadow_minutes`` of 30 minutes, and a cloud mask at 1.5 magnitudes of
extinction. The survey does not require the time before twilight to be
long enough for its visits (``before_twi_check=False``); instead a
``TruncatePreTwiDetailer`` drops visits that would run into morning twilight.
The detailers, in order, are:

#. ``CameraSmallRotPerObservationListDetailer``: camera rotation offset by
   3° per visit within ±55°, with a random offset at each band change.
#. ``SplitDetailer``: for EDFS, a ``EuclidDitherDetailer`` dithers along and
   perpendicular to the line joining the two EDFS pointings; for the other
   fields, a ``DitherDetailer`` dithers each visit by up to 0.2°.
#. ``BandNexp``: u-band visits use a single 38 s exposure.
#. ``BandSortDetailer``: order visits by band.
#. ``LabelRegionsAndDDFs``.
#. ``TruncatePreTwiDetailer``.
#. ``ExtinctionLimitDetailer``: 1.5 magnitudes.

The DDF survey ignores observations from the wide-area, template, twilight,
ToO and Roman surveys, so only DDF visits count toward its script.

.. _sec-tier-templates:

Tier 4: Templates
-----------------

Difference imaging needs template images in every band over the whole
footprint. The template surveys acquire these early in the survey, using
the template footprint (:ref:`sec-footprint`), which is flat over the survey
footprint and excludes areas that already have templates.

Basis functions shared by the Markov surveys
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

The template, long-gaps, pairs and greedy surveys all start from the basis
functions in ``lsst_surveys.standard_bf`` (:numref:`tab-standard-bf`). For a
survey that takes visits in two bands, the depth and footprint terms are
split equally between the two bands.

.. _tab-standard-bf:

.. list-table:: Basis functions from ``standard_bf``, with the default
   weights used by the template, long-gaps and pairs surveys. The greedy
   survey uses different weights (:ref:`sec-tier-greedy`).
   :header-rows: 1

   * - Basis function
     - Weight
     - Purpose
   * - ``M5DiffBasisFunction``
     - 6.0
     - Reward pointings where the current 5σ depth is close to the best
       achievable depth (fiducial seeing 1.3"), including cloud extinction.
   * - ``FootprintBasisFunction``
     - 1.5
     - Reward pixels that are behind their desired number of visits in the
       footprint; pixels outside the footprint are masked.
   * - ``SlewtimeBasisFunction``
     - 3.0
     - Reward pointings that are a short slew from the current position.
   * - ``StrictBandBasisFunction``
     - 3.0
     - Reward staying in the current band, unless the Moon has risen or set,
       twilight has started or ended, or there has been a gap in observing.
   * - ``BandLoadedBasisFunction``
     - 0
     - Require the survey's bands to be mounted.

Each survey adds its own basis functions, the standard masks and its cloud
mask (:ref:`sec-masks`) to this list.

Template surveys
^^^^^^^^^^^^^^^^

Each template survey is a ``BlobPairsSurvey``, generated by
``lsst_surveys.gen_template_surveys``. It covers a contiguous blob of sky
twice, first in one band and then in a second (or the same) band, with the
field tessellation rotated between the two passes and a target time of
25 minutes per pass. In addition to the standard basis functions, each
template survey:

* Counts only visits with good seeing toward the footprint, and masks pixels
  where the current seeing is worse than the template limit. The limit is
  1.2" at zenith in all bands, scaled with declination
  (``declination_dependent_fwhm``); for a pair of bands the smaller limit is
  used.
* Masks pixels which already have the required number of good-seeing visits
  in the first band of the pair.
* Masks pixels which have already been observed by the survey that night,
  so template visits are spread over several nights.
* Restricts the blob to within ±2.5 h of the meridian.
* Only runs outside twilight, with at least 25 minutes before twilight.
  Surveys which include u or g also require the Moon to be below −5°.
* Requires at least 50 deg² of available sky within 90° of the reward peak.
* Does not run if the median cloud extinction above the horizon exceeds 2.0
  magnitudes, and masks pixels with more than 1.0 magnitude of extinction.

The template surveys use the 76° maximum altitude and a ``shadow_minutes``
of 55 minutes. Their detailers set a random camera rotation within ±80°,
order the blob to start near the current altitude, set the u-band exposure
time, label the regions and set a 1.0 magnitude limit for the queue manager.
Template visits are 30 s, or 38 s in u.

The configuration defines three groups of template surveys
(:numref:`tab-templates`), all at the same tier, so they compete on reward.

.. _sec-tier-longgaps:

Tier 5: Long gaps
-----------------

The long-gaps surveys, generated by ``lsst_surveys.gen_long_gaps_survey``,
take a pair of visits early in the night and then a third visit of the same
fields several hours later, giving "triplets" sensitive to slowly moving and
slowly varying objects. There are three ``LongGapSurvey`` objects, for the
band pairs gr, ri and iz. Each combines:

* A ``BlobSurvey`` that takes the initial pair, 33 minutes apart, in the two
  bands. This uses the standard basis functions plus constraints that it runs
  only in the first 120 minutes after evening −18° twilight, only on fields
  rising in the east (hour angle −12 h to −3.5 h), only outside twilight and
  with at least 15 minutes before the next scheduled observation or
  twilight.
* A ``ScriptedSurvey`` that receives the second visit of each pair and
  schedules it to be repeated, in the same band, after a gap chosen at
  random between 2 and 7 hours. The repeat can be taken up to 2 hours either
  side of its scheduled time, at altitude 20°–80°, and is pushed later if it
  would fall in the zenith exclusion region.

The long-gaps surveys run only on the second night of every four
(``night_pattern = (False, True, False, False)``), and only one long-gaps
blob is taken per night. The initial pairs use ``shadow_minutes`` of
71 minutes and the third visits 33 minutes, both with the 76° maximum
altitude and a 2.0 magnitude cloud limit. The scripted third visits ignore
all observations except their own.

.. _sec-tier-blobs:

Tier 6: Pairs
-------------

The pairs surveys, generated by ``lsst_surveys.generate_blobs``, carry out
most of the wide-area survey. Each is a ``BlobSurvey`` that selects a
contiguous blob of fields around the peak of its reward map and observes it
twice, in two bands, with the second visit to each field about 33 minutes
(at most 40 minutes) after the first. The number of fields in the blob is
set from the timing parameters in ``blob_survey_params``
(:ref:`sec-assembly`), and is reduced to fit before twilight or before the
next scheduled observation.

There are seven pairs surveys, for the band pairs ug, ur, gr, ri, rz, iz and
zy. In addition to the standard basis functions (:numref:`tab-standard-bf`),
each pairs survey includes the terms in :numref:`tab-blobs`.

.. _tab-blobs:

.. list-table:: Additional basis functions in the pairs surveys.
   :header-rows: 1

   * - Basis function
     - Weight
     - Purpose
   * - ``VisitRepeatBasisFunction``
     - −20
     - Penalize fields already visited in the past 3 hours, so the survey
       does not return to the same area too soon.
   * - ``NGoodSeeingBasisFunction``
     - 3.0
     - For g, r and i: reward pixels that have fewer than three visits per
       season with seeing better than 0.8" and depth within 0.5 mag of the

   * - ``TimeToScheduledBasisFunction``
     - 0
     - Require at least 15 minutes before the next scheduled observation.
   * - ``TimeToTwilightBasisFunction``
     - 0
     - Require at least 15 minutes before twilight.
   * - ``NotTwilightBasisFunction``
     - 0
     - Only run between evening and morning −18° twilight.

The pairs surveys use the 76° maximum altitude, ``shadow_minutes`` of
71 minutes and a 2.0 magnitude cloud limit. Their detailers set a random
camera rotation within ±80°, order the blob to start near the current
altitude, set the u-band exposure time, flush the blob before any scheduled
observation, label the regions, set the queue-manager extinction limit, and
create the second visit of each pair. The pairs surveys ignore DDF, near-sun
twilight and ToO visits.

.. _sec-tier-twilight:

Tier 7: Near-sun twilight microsurvey
-------------------------------------

The near-sun twilight surveys, generated by
``lsst_surveys.generate_twilight_near_sun``, search for near-Earth objects
and objects interior to Earth's orbit, which are only visible at low solar
elongation. There is one ``BlobSurvey`` for each of r, i and z. They observe
in twilight, toward the Sun:

* The footprint is the area within 40° of the ecliptic and below Dec +30°,
  restricted to the LSST footprint mask.
* Only pointings at airmass below 2.5, within 90° in azimuth of the Sun and
  within 45° solar elongation are allowed.
* The surveys run only when the Sun is above −14.8° and within 25 minutes of
  −12° twilight, so in the bright part of twilight.
* Each field is visited four times, with 15 s exposures, and the sequence is
  cut to fit in the remaining twilight.
* The band for each night is picked at random from riz (falling back to
  another mounted band if needed), so all visits in a night use the same
  band.
* The surveys run only on the first night of every four
  (``night_pattern = (True, False, False, False)``), so they do not run on
  the same nights as the long-gaps surveys.

The reward combines a footprint term (weight 0.1), slew time (3.0), staying
in band (3.0) and a term that rewards bands with fewer visits so far (0.3).
The surveys use the full 86.5° maximum altitude, ``shadow_minutes`` of
20 minutes and a 3.0 magnitude cloud limit. They ignore observations from
all other surveys.

.. _sec-tier-greedy:

Tier 8: Greedy
--------------

The greedy surveys, generated by ``lsst_surveys.gen_greedy_surveys``, take
single visits to fill any time that no higher tier can use: for example in
twilight, when there is not enough time for a blob, or when clouds rule out
the other surveys. There is one ``GreedySurvey`` for each band, ugrizy, each
choosing one field at a time. They use the standard basis functions with
different weights (:numref:`tab-greedy`).

.. _tab-greedy:

.. list-table:: Basis function weights in the greedy surveys.
   :header-rows: 1

   * - Basis function
     - Weight
   * - ``M5DiffBasisFunction``
     - 3.0
   * - ``FootprintBasisFunction``
     - 0.75
   * - ``SlewtimeBasisFunction``
     - 3.0
   * - ``StrictBandBasisFunction``
     - 100
   * - ``VisitRepeatBasisFunction`` (visits in the past 2 hours)
     - −1.0

The large weight on staying in band means the greedy surveys almost never
change filter. The u and g surveys only run outside twilight with the Moon
below −5°. The greedy surveys use the 76° maximum altitude and
``shadow_minutes`` of 15 minutes, and have no cloud mask: they steer away
from clouds through the depth term, but are not blocked by them, so that the
scheduler always has something to observe. Their detailers set a random
camera rotation, label the regions and set the u-band exposure time. They
ignore DDF, near-sun twilight and ToO visits.
